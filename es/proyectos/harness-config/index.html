Harness Config

El dolor en mi flujo QA

La configuración del agente se reinventaba por sesión: MCPs que faltaban, claves copiadas entre terminales y roles asignados "como siempre". Dos máquinas daban resultados distintos con el mismo ticket, y nadie sabía quién decidía el modelo por defecto.

2 configuracionesdos lugares, sin fuente única

Cómo lo usa un QA

Dos mitades responden dos preguntas distintas de la sesión. El comando las resuelve juntas y deja rastro auditable.

Pregunta QADónde se responde
¿Cómo queda configurada la sesión (MCPs, tooling, proveedores)?Mitad configuración — el comando aplica el setup del harness en un solo paso, con defaults versionados.
¿Qué modelo y rol usa cada agente?Mitad roles — asignación explícita de rol→modelo, sin adivinar quién corre con qué.
¿Qué pasa si un modelo desaparece o cambia?Selector con fallback — el rol cae a un modelo vigente y el cambio queda visible.
¿Cómo vuelvo a un estado sano?Defaults y ayuda integrados — restaurar o consultar el estado actual es parte del mismo comando.

En mi kit de trabajo

La chuleta completa vive en la presentación; estas son las órdenes que uso cada día.

bun run harness-configAplica las dos mitades: config + roles
bun run harness-config-helpConsulta el estado y las opciones
bun run harness-config-defaultRestaura los defaults versionados
bun run harness-config:roles:testTests del selector de modelos/roles
  • Gates de calidad: tests del selector de roles en cada cambio del flujo.
  • Reversibilidad: todo estado aplicado tiene vuelta a defaults.
  • Decisiones explícitas: el modelo por defecto se declara, no se hereda por costumbre.

Qué demuestra

Automatización de entornos

Convierto setups manuales repetidos en comandos reproducibles con tests.

DX para QA

Un comando, ayuda integrada y rollback: menos fricción entre escribir tests y correrlos.

Gobernanza de modelos

Rol→modelo explícito con fallback: sé qué modelo ejecuta cada agente y por qué.
