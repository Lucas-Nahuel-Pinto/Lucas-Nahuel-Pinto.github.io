The pain in my QA flow

Every machine had its harness its own way: unregistered skills, MCPs nobody knew were active, agents with inherited models, and scripts only the author could run. Knowing what was installed meant reading config files by hand, machine by machine, and every change was an edit with no safety net.

Zero panoramaof what is installed in each harness

How a QA uses it

Each tab answers one concrete harness question. The site never touches files: the local agent applies only the changes I confirm.

QA questionWhere it gets answered
What does my harness have installed today?Summary — KPIs for skills, commands, agents, MCPs, env, scripts and registries, with clickable H-J health cards.
Which skills and commands exist, and are they registered?Skills + Commands — sortable table with tier, references, evals and registration state.
Which model runs each agent?Agents & Models — model catalog picker with diff and confirmation before applying.
Which MCPs are active and which variables do they use?MCPs + Env — MCP toggles over config and a .env.example vs .env presence matrix, values never read.
Can I run the harness scripts from here?Scripts + Registries — runner whitelisted to package.json names, with an output pane.
How do the pieces connect to each other?Graph — relational graph of skill→refs→scripts, agent→skills, MCP→env with selection illumination.

In my working kit

The whole flow fits in four commands, always from the manager repo directory:

bun run agent [code]Headless agent: pairs with the site through the relay
bun run pullScans the harness and validates the snapshot (diagnostic CLI)
bun run build:onlineUI build for the hosted origin
bun run repo:checkFull gate: format, lint, types and tests
  • Actions with a safety net: diff on screen, explicit confirmation, atomic write and automatic re-scan.
  • Outbound-only connection: the agent opens a single connection to the relay; no inbound ports, no firewall changes.
  • Secrets out of the snapshot: .env is read by presence, never by value, and frames travel end-to-end encrypted.

What it demonstrates

Security-by-design architecture

The relay is a blind courier that only forwards: keys, codes and paths never leave the encrypted channel.

Harness automation

I turn manual management of any harness into a reproducible panel, with tests in the middle.

Confirmation-first DX

No change writes blindly: every action shows its diff and waits for my OK before touching a file.

Closing

Six tabs, a windowless agent and a blind relay: any harness administered from the browser without lowering the guard.
