Jira Traceability Manager

I turn manual traceability audits into a 5-view dashboard: what is covered, what broke and what risk exists, in a single pull.

  • Traceability
  • Risk
  • Data-driven QA
View code — jira-traceability-manager

The pain in my QA flow

Traceability lived scattered across Jira, Xray and spreadsheets. Knowing whether a story was truly covered meant following links by hand, story by story. The gaps — orphan stories, empty epics, bugs without a story — showed up when someone needed them, not before.

2-3 hoursof manual audit per sprint

How a QA uses it

Each view answers one concrete quality question. None of them shows how the code is built: only what it means for the release.

QA questionWhere it gets answered
What does each story actually cover?Tree — the Epic→Story→ATP→ATR→TC hierarchy at a glance, with gaps flagged.
Where does the traceability chain break?Graph — the real links between entities; unconnected nodes stand out.
Which components have hollow coverage?Matrix — story × component: empty cells = release risk, not code risk.
What is broken TODAY?Alerts — orphan stories, empty epics, bugs without a story and open blockers, always in sight.
Is it improving sprint over sprint?Metrics — coverage, pending work and trend to decide with data, not feelings.

In my working kit

One command refreshes the snapshot; the dashboard is a static file I can open, share or archive per sprint.

bun run trace:pullDownload the Jira/Xray snapshot
bun run trace:refreshPull + rebuild the dashboard
bun run buildBuild the 5-tab app (single file)
bun testTested pipeline: schema validation and alerts
  • Quality gates: schema validated with ajv before rendering, alerts as tested rules.
  • Fail-safe: a corrupt snapshot is reported instead of rendering fake numbers.
  • Evidence-based review: every metric audits back to its original link, not a spreadsheet.

What it demonstrates

Traceability

I follow every finding to its story and every story to its evidence: the full chain, not a loose status.

Data-driven QA

Release decisions come from reproducible metrics and alerts, not the team's memory.

Risk over volume

The dashboard prioritizes the gaps that break the release (orphans, empties, blockers) over raw test counts.

Closing

From manual audit to one command and 30 seconds. The repo is public (MIT license) and the demo runs on synthetic data you can regenerate.
