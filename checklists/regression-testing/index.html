Execute (Phase 1)

  • detalles

    Cada stage (trigger, monitor, download) se ejecuta vía gh: sin auth nada del pipeline corre. Verificar también gh repo view y gh workflow list.

  • detalles

    Ejemplos: gh workflow run regression.yml -f environment=staging -f video_record=false -f generate_allure=true · sanity: -f grep="@auth" O -f test_file="tests/e2e/auth/login.test.ts".

    El RUN_ID se guarda apenas se captura — todos los pasos siguientes (watch, logs, downloads) lo usan, y es lo que permite re-engancharse si se pierde la sesión.

  • detalles

    gh run watch puede hacer timeout en suites largas; el polling es el plan B. conclusion solo aparece al completar: success | failure | cancelled | timed_out.

    Phase 2 no arranca hasta completed — analizar un run en vuelo produce métricas a medias.

  • detalles

    La URL de GitHub Pages solo está viva si el job "Build & Deploy Allure Report" terminó verde; si falló, 404 — analizar desde los artefactos descargados.

Analyze (Phase 2)

  • detalles

    Metadata inline: gh run view <RUN_ID> --json status,conclusion,jobs,… · --log-failed (nunca --log: supera 50 MB) · listar artefactos con --json artifacts.

    Nunca saltarse esta descarga en builds rojos (anti-pattern R4): la evidencia expira con la ventana de retención.

  • detalles

    El label suite de Allure deriva del tag de Playwright (@smoke/@regression/@integration…) que también define el scope de CI — single source of truth, nunca reconciliar contra otro set de labels.

  • detalles

    Excluir KNOWN-BLOCKED del pass-rate de gating: computar sobre Total − KNOWN-BLOCKED y reportar el conteo de blocked aparte con cada {BUG-KEY} — ni infla ni deprime el score.

    Run anterior: gh run list --workflow=… --limit=2 → .[1].databaseId → download a ./analysis/previous/.

  • detalles

    Nunca marcar REGRESSION sin mirar la historia primero — es la clasificación errónea más común.

    Patrones ENVIRONMENT: ECONNREFUSED, ETIMEDOUT, net::ERR_, navigation timeout, browserType.launch, 502/503, context deadline. Ojo: ECONNREFUSED a la API propia probablemente = app caída, no "infra"; ENVIRONMENT solo si muchos tests no relacionados fallan en el mismo host.

    Impacto: REGRESSION bloquea release · FLAKY/ENVIRONMENT/KNOWN no bloquean · KNOWN-BLOCKED excluido del pass-rate · NEW TEST requiere verificación manual antes de creerlo.

  • detalles

    Este repo corre con retries: 0: un test flaky aparece como failure intermitente (regla >20% historia), nunca como "pasó al retry". (Anti-patterns R1.)

  • detalles

    Clasificación = qué pasó · Severidad = cuánto importa. Ambas ejes se reportan por fallo.

  • detalles
