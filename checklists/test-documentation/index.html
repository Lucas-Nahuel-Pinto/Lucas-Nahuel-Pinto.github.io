Alcance

  • detalles

    La mayoría de escenarios de cualquier scope terminará Deferred.

  • detalles

    La exploración pertenece a /sprint-testing. Documentar comportamiento no validado congela supuestos en el repositorio de regresión: cada TC que cuelga de un resultado no verificado se convierte en ruido que alguien ejecutará y descartará.

    Es el hard prerequisite del skill — sin él, el workflow no arranca.

  • detalles

    No every bug becomes a regression Test: un typo one-time en un área estable se trata como failed test (fix ya verificado en sprint-testing) → Deferred. Pero si es regression-worthy, debe terminar con un Test que lo cubra en AMBAS modalidades — donde hay un bug importante, debe existir un test que lo atrape de nuevo.

    1. ¿Es candidato a regresión? (filtro Phase 0 Q2 + ROI; el prior-bug rule sesga hacia arriba) → NO: Deferred, fin.
    2. ¿Salió de un Test ya ejecutado? → SÍ: reusar ese Test para el retest + regresión, link tests / is tested by al bug. NO: crear y diseñar el Test nuevo, link igual.

    Esta regla overridea el "the bug is the test case" de sprint-testing — esa frase cubre solo el retest in-sprint, no la regresión futura.

  • detalles

    Los Candidates de este skill son el input de planificación de /test-automation, que re-scopes cada uno a su propio modelo. Los ad-hoc Candidates entran bajo el scope que mejor encaje (lote de módulo o regression-driven para un TC suelto).

    Un verdict sin bucket Candidate/Manual/Deferred es un error: no hay cuarto outcome. La cadena completa es derive (sprint-testing) → document (este skill) → automate (/test-automation).

Análisis (Phase 1)

  • detalles

    Lectura detallada vía bun run jira:sync-issues get <STORY> --include-comments — nunca acli view (devuelve null para custom fields). Leer todo el folder materializado, no solo un campo: ACs, scope, business rules y comentarios dan contexto que un solo campo omite.

    ATP/ATR según modality: jira-native → acceptance-test-plan.md / acceptance-test-results.md (campos Story sincronizados); jira-xray → test-plans/TESTPLAN-*.md / test-executions/TESTEXEC-*.md + estado por TC via /xray-cli. Escenarios ya existentes → no reinventar.

    El glossary fija el vocabulario de nombres, pasos y preconditions — términos canónicos, anti-glossary prohibidos.

  • detalles

    El ATP se escribió ANTES de que existiera el código. Tres pasos: listar archivos que toca la implementation plan, grepear el código real, comparar. Discrepancias comunes: un API que el ATP asumía resulta ser SSR/direct DB; formato de texto del ATP vs realidad ("based on N reviews" vs "(N reviews)"); IDs hardcodeados vs patrón variable.

    Skipping this step es la causa más común de tests automatizados inválidos después. Las correcciones quedan en una sección Refinement Notes del TC.

  • detalles

    Mismo TC: credenciales válidas + submit login → redirect + token + welcome (tres aserciones, un TC).

    TCs distintos: misma acción de login pero precondiciones distintas → credenciales válidas / cuenta locked / credenciales inválidas son TC separados (el precondition cambia).

    Splittear un par (precondition, action) en N "check panel" TCs es el anti-patrón más diagnosticado en reviews — el merge es solo dentro de una partición, nunca entre particiones, boundaries o estados.

Priorizar — ROI (Phase 2)

  • detalles

    Q1: typo one-time en área estable = no protege nada futuro → defer. Q2: prior bugs → priorizar incluso con ROI moderado ("falló una vez, puede volver a fallar"). Q3: XSS / a11y / performance / responsive son suites APP-level, no TCs por feature → defer de este scope.

    Son puertas, no scoring: fallar un filtro no se compensa con ROI alto.

  • detalles
    Factor15
    FrequencyYearly / rarelyEvery PR / commit
    Impact (si falla)CosmeticRevenue / core business
    Stability (del flujo)Very volatileUnchanged for months
    Effort (a automatizar)TrivialVery high (week+)
    DependenciesNoneComplex externals

    Un "critical flow" con Effort=5 y Dependencies=5 tiene ROI bajo por diseño — es correcto, no un bug de la fórmula (gotcha del skill).

  • detalles

    Un atomic de ROI bajo (authenticateSuccessfully) puede volverse automatizable puramente por reuse: cada flow E2E que lo consume le suma un 20% al score.

    Aplicar solo cuando el TC realmente se reutiliza — N inflado artificialmente sesga el veredicto igual que cualquier otro número inventado.

    Modality cambia el verbo en Phase 3, no el veredicto: los 3 verdicts son idénticos; jira-native crea Tests solo para Candidate+Manual, jira-xray promueve los regresionables al Regression Test Plan y los enriquece.

  • detalles

    Tres capas, tres counts: (1) derive/analizar (sprint-testing): considerar muchos casos 1:N — vive en el análisis, aún no en el TMS; (2) documentar (este skill): TC persistente solo si vale la pena re-ejecutarlo; (3) automatizar (/test-automation): los Candidates. "analyzed 80 → documented 12 → automated 8" es la forma sana — nunca "document all 80". En jira-xray el "document 12" = promover 12.

    La banda 1.5-3.0 es "case by case: ¿prior bug? ¿critical flow? si no → defer"; 0.5-1.5 "probably defer: include only if prior bug". El prior-bug rule overridea los umbrales: un escenario atado a un bug cerrado entra a regresión aunque su ROI solo dé 1.5-3.0.

Documentar en TMS (Phase 3)

  • detalles

    Es el QA process epic del three-axis model: parent = "¿qué bucket QA sigue este Test" — nunca épica de producto/dev, nunca sin parent. El área de producto viaja en components, la cobertura de Story en los issue links — tres ejes separados.

    Al crear: escribir la test-repository strategy en su description y cachear la key en qa.qa_epics.test_repository_epic.key. Label QA-Artifact es la identidad obligatoria de toda épica de proceso QA.

  • detalles

    Coverage truth (live-verified): SOLO el link ATS→Story is tested by llena el panel de cobertura Xray. Los links Story↔ATP y Story↔ATR son trazabilidad administrativa — keeperlos, pero jamás contarlos como cobertura.

    ATS: contiene TODOS los TCs de la Story, es el ancla de cobertura y su components son obligatorios (heredados de la Story — la excepción de components aplica SOLO al TS feature-level). TS: agrupación opcional 1:1 con Epic/module (TS: <EPIC-KEY|module>: Validate <feature>), components opcionales; solo entran Tests promovidos, los Deferred del sprint no.

    Jerarquía de contenedores: Regression Epic = paraguas · ATS = cobertura por Story · TS = agrupación feature · Test Plan = scope de ejecución.

  • detalles
    1. Find-or-create ATS → link a Story (coverage-panel link).
    2. Find-or-create ATP → link a Story (administrativo).
    3. Create ATR → link a Story (administrativo).
    4. Update ATP → link ATR (plan/results bidireccional).
    5. Por cada TC: create → add al ATS → link ATP ("designed by") + ATR ("executed by"). Sin link directo TC→Story mientras exista ATS.
    6. Derivar las listas de tests del ATP y ATR desde la membresía del ATS.
    7. Promoted TCs → Regression Test Plan / TS + label + rename + transition (ver t9).

    Crear el primer TC antes de los contenedores deja referencias huérfanas — el único arreglo es fix-traceability. Esta asimetría con /sprint-testing Stage 1 (que crea TCs primero) es intencional: module-driven Stage 4 pre-crea targets porque el sharding paralelo los necesita existentes.

  • detalles

    Xray Cloud silently droppea steps inline en el create — para un Manual Test: crearlo vacío de steps, luego Add Test Step uno a uno (verificar opcional con Get Test). Cucumber no se ve afectado (el Gherkin es un campo único).

    Xray requiere dos llamadas: Create Test (registra en Xray) + Update Issue (pega el Description completo). Saltarse la segunda deja un TC sin documentación legible en Jira.

    Description siempre con el template completo: Related Story, Priority, ROI, Prior bugs, Test Design (gherkin/steps), Variables table, Implementation Code, Architecture, Test IDs, Preconditions, Expected Results.

  • detalles
    • Variables: {mentor_id}, nunca 550e8400-… — cada variable con query de cómo obtenerla en runtime.
    • Tags siempre: prioridad (@critical|@high|@medium|@low), suite (@regression, @smoke si critical path), @automation-candidate, trazabilidad @{US_ID}.
    • Comentarios: # === PRECONDITIONS ===, # === ACTION ===, # === VALIDATIONS ===, # === EQUIVALENT PARTITIONS ===.
    • Docstring: Bugs covered, Related Story, ROI. Particiones en Examples: Happy path / Examples: Edge case.
  • detalles

    El prefijo es SIEMPRE la key de la User Story, en cada modalidad. CORE = comportamiento asserted tras should; CONDITIONAL = cláusula when/if opcional. Vocabulario desde domain-glossary.md si existe.

    Validate <feature> está reservado al layer de agrupación (Test Set summary / describe()), nunca a un caso individual. En KATA: @atc('PROJ-101') con la key del TC.

    Anti-patróns a rechazar: "Login test", "Login - error", "TC1: Test form". El rename usa [ISSUE_TRACKER_TOOL] Update Issue --summary — paso obligatorio, no opcional.

  • detalles

    Transiciones: start_design · ready_to_run · for_manual (→ Manual terminal) · automation_review_from_ready (→ In Review) · approve_to_automate (→ Candidate terminal). Nombres desde .agents/jira-workflows.json vía {{jira.status.test_case.*}} / {{jira.transition.test_case.*}}.

    In Review = "ROI under evaluation"; Candidate = "Approved for automation" — el terminal de un Candidate es Candidate, no In Review. Deferred TCs quedan en READY sin promover. Dejar promovidos en READY bloquea el regression backlog.

  • detalles

    Status se va moviendo con la vida del TC: automation-candidate al promover como Candidate, manual-only si es Manual; al automatizarse → automated y quitar automation-candidate.

    Priority opcional: critical / high / medium / low. Taxonomía completa en tms-conventions.md §Labels.

  • detalles

    En xray el label va vía [ISSUE_TRACKER_TOOL] — xray-cli no tiene update-label para Tests existentes. Transition según veredicto (ver t7): Candidate camina READY → In Review → Candidate completo porque el veredicto ES la aprobación a automatizar; Manual → for_manual.

    El rename canónico (t6) y la transición (t7) son pasos obligatorios de la promoción, no mejoras opcionales — el regression repository hereda lo que se promueva sin normalizar.

  • detalles

    El ATS queda en Designing hasta Stage 4 porque estos tres campos dependen de la evaluación VCR, que recién existe después del ROI. Rellenarlos con [ISSUE_TRACKER_TOOL] Update Issue (textarea → formato ADF), luego transicionar vía la transición Done (--status "Close").

    Saltarse este paso deja ATSs eternamente en Designing aunque sus TCs ya estén promovidos.

Cierre

  • detalles

    Este skill CREA los Test issues, los linkea a la Story, corre el sync y lee los archivos materializados — jamás escribe a mano dentro de test-cases/. Jira es la fuente de verdad.

    Además da a /test-automation un handoff inmediato: los per-TC .md ya están materializados sin re-leer el TMS.

  • detalles

    La matriz es el entregable congelado de la sesión — sobrevive al Archive del .session/ y es lo que se commitea. El reporte final cierra la fase: qué se documentó, veredictos y trazabilidad completa.

    Los test-cases/*.md son caché gitignored, recuperables con bun run context:hydrate — no son entregable.

  • detalles

    Dos bloques chat-facing de session-footer-contract.md: (1) screenshots consolidados (bug annotations primero, y el path se surfacea en-flow en cuanto existe); (2) Session Footer con los campos skills_loaded, mcps_used, clis_used, testing_levels_touched, screenshots_captured — niveles esperados pero no tocados llevan "none" explícito.

    Sesiones multi-subagent: cada stage report lleva los 5 campos y el orchestrator compila el footer una vez al cierre. Framing de este skill: curation. Jamás dentro de un comentario Jira ni de un cuerpo de ATR.

No hacer

  • detalles

    Un Test Plan sin trazabilidad a Story/Epic es inauditable; TCs creados antes de ATS/ATP/ATR dejan referencias huérfanas y fix-traceability es el único arreglo. (Anti-pattern D2 + Gotcha "linking order is not optional".)

  • detalles

    Duplicar la especificación dentro del TC crea dos fuentes que divergen cuando el comportamiento cambia. El TC documenta identidad (precondition + action + outcome) y trazabilidad — la ejecución detallada vive en el test automatizado. (Anti-pattern D3.)

  • detalles

    Sin scoring, "candidato a automatizar" es una opinión, no una decisión. Y un Deferred no es un TC flojo: en jira-native no se crea; en jira-xray el sprint Test queda sin promover. (Anti-pattern D4 + Three outcomes.)

  • detalles

    Phase 0 resuelve la modalidad una vez y queda sticky en plan.md. Mezclar contenedores de ambos mundos (un Test Plan item + un campo Story en la misma Story) deja trazabilidad irreconciliable. (Anti-pattern D5.)

  • detalles

    Un customfield_NNNNN hardcodeado drifta en silencio cuando la instancia cambia: la escritura "funciona" pero apunta al campo equivocado. Los catálogos .agents/jira-fields.json / jira-required.yaml son el catálogo canónico. (Anti-pattern D6.)

  • detalles

    Un plan con N resultados no tiene sentido: cada corrida se registra contra SU plan. Múltiples ATRs colgando de un ATP sí es válido (corridas distintas). (Anti-pattern D7.)

  • detalles

    El historial del bug es inmutable: su cierre documenta que el fix se verificó. El vínculo con la regresión futura es una issue link desde el TC nuevo, no una reescritura del pasado. (Anti-pattern D8.)

  • detalles

    Coverage truth live-verified (2026-08-21): los links ATP→Story y ATR→Story son trazabilidad administrativa y contribuyen zero cobertura. Se conservan para auditoría, pero reportar "la Story está cubierta" por ellos es un reporte falso — el panel solo se llena por ATS→Story.
