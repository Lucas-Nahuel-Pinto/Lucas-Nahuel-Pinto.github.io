Preparación

  • detalles

    Son los mapas de negocio (features, entidades, endpoints) y el plan maestro de pruebas. Sin ellos el ATP se redacta "a ciegas": los nombres de entidades no coinciden con el dominio, no sabes qué módulos ya están priorizados para regresión y las preguntas al PO salen genéricas.

    El skill exige parar y derivar a /project-discovery en vez de improvisar — un ATP escrito sin contexto es el desperdicio más caro del ciclo.

Entrada

  • detalles

    Jira es la fuente de verdad; el script genera archivos .md sincronizados en la carpeta PBI que son la lectura canónica. acli workitem view devuelve null para custom fields (ACs, ATP, campos QA) — leer por ahí produce tickets "vacíos" falsos.

    Los comments importan: ahí vive la Team Discussion (decisiones del PO, notas técnicas, edge cases ya debatidos) que evita re-preguntar lo resuelto.

  • detalles

    El STP (Sprint Test Plan) es el planificador vivo del sprint: qué tickets se probaron, cuál va el estado, cuál falta. Se crea solo en el primer ticket del sprint; los siguientes lo actualizan (añaden el ticket + progreso).

    Se parenta a la épica de proceso QA Master Test Plan (nunca a una épica de producto) para que todos los planes de prueba del proyecto cuelguen del mismo bucket y el resto de QA pueda encontrarlos. Si la instancia no tiene work type Test Plan — el caso típico es no usar Xray, porque los tipos Test Plan / Test Execution / Test Set los añade la app de Xray —, se salta con nota (no bloquea): a altura de sprint no hay campo custom donde volcar el STP, así que se documenta el warning y el plan del sprint sigue en el archivo local plan.md.

  • detalles

    Dos acciones que hacen visible el trabajo de QA en el tablero:

    • start_testing mueve la Story de Ready For QA a In Test — el equipo ve que QA la tomó. Nunca hacerlo sin antes explicar la historia al usuario y recibir su OK (es un gate de contexto, no un trámite).
    • qa_assignee es el custom field del dueño QA de la Story o del ticket del bug — distinto del assignee nativo (que queda para dev). Regla read-before-write: solo se escribe si está vacío; jamás pisar un owner existente salvo handover explícito y justificado.

Planificación (Stage 1)

  • detalles

    Si la Story pasó por /shift-left-testing pre-sprint, el análisis crítico, la calidad de la Story y las ACs refinadas ya están escritos en el campo ATP de Jira. Rehacerlos in-sprint es trabajo duplicado.

    Condiciones del atajo: label shift-left-reviewed + label datado con menos de 30 días + que las ACs sigan coincidiendo con la descripción actual (si la Story cambió, se invalida y se re-ejecuta el análisis completo — barato comparado con actuar sobre refinamiento viejo). Se lee el ATP sincronizado acceptance-test-plan.md, nunca un archivo local.

    Lo que SÍ se completa in-sprint es lo que shift-left dejó a propósito con "solo nombres" (solo los nombres de los outlines, sin ejecutarlos todavía): tablas de parametrización, pasos numerados, test-data JSON y estrategia de datos con Faker.

  • detalles

    El triage decide cuánta QA merece el ticket antes de invertir en planificar:

    • Veto (gana siempre sobre el score): cambios sin comportamiento (CSS, docs, copy, refactor limpio) → solo revisión de código + comentario. No hay bug que encontrar porque no hay comportamiento nuevo.
    • Fuerza Full: dinero, integridad de datos, auth, integraciones externas, cálculos → Full obligatorio aunque el score salga bajo. Aquí un escape cuesta caro.
    • Risk score (si no hay veto): factores como funcionalidad nueva (+3), datos dinámicos (+3), ACs explícitas (+2), UI visible (+2)… El score define la profundidad, no si se prueba.

    Notación: ticket = contenedor en Jira (issue): ticket del bug (post-release) o ticket de defecto (pre-release). defecto = el problema encontrado pre-release; bug = el problema encontrado post-release. reportar = el verbo. En los tickets del bug el flujo de decisión (veto → score) corre antes de escribir el ATP. Tres puntos para no confundirse:

    • El ATP va en el ticket del bug/defect, no en la Story vinculada. Cada ticket del bug/defect a retestear tiene su propio ATP y su propia ATR (retest Execution ReTest: {BUG-KEY}), guardados en ese ticket: campo acceptance_test_plan del bug/defect / ítem ATP: {BUG-KEY}. La Story mantiene el suyo. El link Story↔bug/defect es solo trazabilidad, no hereda planes.
    • Al ATP de ese ticket se le agrega el Bug Analysis: pasos de reproducción, expected vs actual, y chequeo de integridad de datos si el defecto tocó estado persistido.
    • No confundir con el defecto que tú reportas al probar una Story: al reportarlo solo creas un ticket de defecto nuevo (repro + severidad + evidencia), todavía sin ATP. El ATP de ese ticket nace cuando el fix llega a staging y entra a QA para retest.

    Por eso el veto va primero: si el fix es solo un typo, CSS o docs sin cambio de comportamiento, se resuelve con code review y no se gasta un ATP completo en verificarlo.

  • detalles

    Antes de diseñar tests, verificar que para cada AC existan datos con los que realmente poder probarla en staging. Un AC no es testeable si no puedes llevar el sistema al estado previo que exige.

    • Discover — el dato ya existe tal cual (hay pedidos pagados → probar filtro "pagados").
    • Modify — existe base y hay que alterarla (promover un usuario a Admin).
    • Generate — crearlo desde cero (crear cupón vía API/DB/UI para probar cobro).

    Si ninguno aplica, el AC queda blocked. El check corre antes de los outlines porque diseñar tests para un AC sin path de datos es trabajo tirado — no podrías ejecutarlos. Un AC veto-level sin datos se escala al usuario de inmediato; los menores se registran como DATA-FEASIBILITY en el ATP para que PO lo vea al estimar (puede mover la story o pedir pre-work).

    Ejemplo: AC "reembolso parcial calcula 70%" — si staging no tiene pagos ni endpoint de pasarela, el outline "Should refund 70% correctly" es papel mojado.

  • detalles

    Ancla la Story a la realidad: qué persona/qué KPI toca (business), qué endpoints/tablas/componentes toca (técnico), y una tabla de complejidad (lógica, integración, datos, UI) que define las expectativas de cobertura y estima el esfuerzo — insumo para la estimación de PO.

    La herencia de épica evita duplicar: si en el feature plan ya se respondió un riesgo o una integración, se cita ("ver FTP de la épica"), no se re-deriva ni se vuelve a preguntar al PO. Las preguntas son el recurso más escaso de una sesión de grooming.

  • detalles

    Es el corazón del valor de QA en planning: los defects nacen de requisitos ambiguos, no de código malo. Se buscan:

    • Ambigüedades — "el usuario puede iniciar sesión" ¿HTTP 200 o toast? Sin definir, no hay asersión posible.
    • Gaps — AC sin camino de error, regla de negocio no escrita.
    • Edge cases no en la Story — OTP después de expirar sesión, whitespace en inputs…
    • Testabilidad — veredicto Yes/Partial/No: ¿el AC se puede verificar objetivamente? ("funciona rápido" sin métrica = No).

    Si la Story está clara, se dice "sin problemas" — inventar preguntas para llenar checklist es anti-patrón: entrena al equipo a ignorar la salida de QA.

  • detalles

    Las ACs originales se reescriben como escenarios ejecutables: Given (estado inicial + rol + datos), When (acción con valores exactos — "john+test\@example.com", no "email válido"), Then (resultado UI + status/body API + cambio en DB).

    1:N por defecto: una AC no trivial implica varios escenarios (partición válida + cada inválida + fronteras). Colapsar a uno solo requiere justificación escrita trivially atomic. El número lo deciden las técnicas de diseño, no un mínimo fijo.

    Todo comportamiento inferido (que QA dedujo, no está literal en la Story) se marca NEEDS PO/DEV CONFIRMATION — el marcador va literal al Jira para que PO lo vea en planning y decida.

  • detalles

    Las técnicas se aplican por trigger del AC (no a elección arbitraria):

    • EP (equivalencia) — siempre, todo input tiene particiones válidas/inválidas.
    • BVA — si hay rango/límite/longitud/ventana de fechas (min-1, min, min+1…).
    • State-Transition — campos con estado/ciclo de vida (cada transición válida e inválida).
    • Decision Table — +2 condiciones que interactúan (rol × flag × estado).
    • Pairwise — +3 factores combinables (browser × locale × plan), con log de la reducción.

    Un AC con rango sin outlines BVA = plan incompleto. La parametrización agrupa el mismo comportamiento con datos variados (evita duplicar steps), los pasos numerados con datos exactos y el test-data JSON hacen el outline ejecutable por cualquier tester — esto es lo que el ATP pre-sprint solo esbozó con nombres.

  • detalles

    El glosario define el vocabulario canónico del dominio ("pedido" no "orden", "socio" no "partner"). Usarlo en nombres de tests/ACs evita que Xray se llene de sinónimos que rompen búsquedas y comparaciones.

    Si aparece un término nuevo o ambiguo durante la prueba, se marca en el comentario QA para que PM lo agregue por el protocolo de cambio del glosario — nunca editar el glosario desde una sesión de QA.

  • detalles

    Es el extracto que PO ve de un vistazo en el UI de Jira durante planning — el ATP completo está en su campo/ítem, esto es el resumen accionable. Regla de oro: leer la descripción actual primero y agregar la sección al final; sobrescribir destruye el contenido original del equipo.

    Si la Story ya venía de shift-left, se actualiza la sección (mismo heading, fecha nueva), no se duplica.

    • detalles

      La versión ejecutable de las ACs — es lo que Dev usa para implementar y PO para aceptar. Es canónica: vive también en el campo acceptance_criteria si existe.

    • detalles

      Copia de la tabla de edge cases detectados (escenario / ¿en la Story? / criticidad / acción). PO decide aquí si se agrega al AC o solo se prueba — es el primer filtro de scope.

    • detalles

      Reglas que QA extrajo del análisis y que la Story no decía literalmente (ej. "los cupones no son acumulables con puntos"). Cerradas aquí, no se rediscuten en ejecución.

  • detalles

    El ATP (Acceptance Test Plan) es el artefacto de planning: lo que PO/Dev usan para estimar, lo que Stage 2 (Ejecución) ejecuta y lo que fix-traceability valida después. Contenedor según modalidad:

    • jira-xray → ítem Test Plan ATP: {KEY}: {title} (find-or-create desde el campo), descripción = cuerpo completo.
    • jira-native → campo acceptance_test_plan de la Story; si el campo no existe, comentario ## Acceptance Test Plan (ATP) (fallback, nunca bloquear).

    Un solo ATP por Story — si shift-left ya escribió el campo, se expande ese mismo ATP (superset), nunca se crea una segunda versión "(DRAFT)" que después haya que reconciliar.

    • detalles

      El flag de estado distingue el ATP in-sprint del pre-sprint (shift-left usa "Refined — Awaiting PO Estimation"). Marca en qué fase de vida está la planificación para quien lo abre frío.

    • detalles

      Responde "¿por qué importa probar esto y qué tan difícil es?". La tabla de complejidad y el esfuerzo estimado son los números que PO usa para decidir si el ticket entra al sprint con este alcance.

    • detalles

      Las 4 tablas (ambigüedades / gaps / edge cases / contradicciones) + veredicto Yes-Partial-No. Es lo que convierte "testear la Story" en "arreglar los requisitos antes de que Dev codee sobre supuestos".

    • detalles

      Cada AC original explotada en escenarios Given/When/Then con Type (Positive/Negative/Boundary/Edge) y Priority. El tipo/prioridad determinan el orden de ejecución en Stage 2 (Ejecución); el marcador de confirmación filtra lo inferido.

    • detalles

      El motor ejecutable del ATP. La tabla de cobertura debe mostrar 0 explícitos en tipos vacíos — ocultar ceros sesga la estimación de PO.

      Cada outline = título "Should <comportamiento> <condición>" + precondición + pasos con datos exactos + esperado por capa (UI mensaje, API status+body, DB fila/campos). Esto es exactamente lo que shift-left dejó como "solo nombres".

    • detalles

      Define con qué se prueba: datos estáticos (críticos, hardcodeados a propósito), dinámicos con Faker (masivos), y cleanup para que los tests sean idempotentes e independientes de orden — sin esto, la segunda corrida falla por datos sucios.

    • detalles

      Veredicto (Good / Needs Improvement / Significant Issues) + las preguntas separadas por audiencia: las de PO bloquean sprint planning, las de Dev bloquean implementación. Cada pregunta lleva contexto + impacto si no se responde + sugerencia.

    • detalles

      Cierre operativo: bloqueos de datos (con pre-work requerido), estrategia pre/durante/post-implementación, matriz riesgo→mitigación (qué outlines cubren qué riesgo) y los pasos siguientes con puntero a /test-documentation.

  • detalles

    Marker suave del ecosistema QA: indica que la Story ya pasó por refinamiento QA. Junto con el label datado shift-left-{fecha} es lo que permite detectar frescura (<30 días) para el short-circuit de la próxima pasada. Los labels se añaden, nunca se reemplazan — los viejos documentan la línea de tiempo.

  • detalles

    El grafo de Jira tiene 3 roles distintos y mezclarlos rompe la trazabilidad:

    • Parent (épica de proceso) — agrupa los artefactos QA por tipo (plan / ejecución / tests / defects). Nunca una épica de producto.
    • Link test ATS→Story — el único que llena el panel de cobertura de Xray. Sin él, Xray cree que la Story no está cubierta aunque haya 20 TCs.
    • Links ATP→Story y ATR→Story — trazabilidad administrativa (cero cobertura) pero obligatorios para que el grafo Jira esté completo.

    La membresía TC→ATS es interna de Xray (GraphQL), nunca issue links — ahí solo existe la excepción jira-native sin work type Test Set.

    • detalles

      Si shift-left ya pobló el campo, el ítem nace de ahí (sembrando su descripción) — el campo es la fuente pre-sprint, el ítem es su hogar in-sprint. Si el campo está vacío (Story sin shift-left), se crea el ATP completo automáticamente en ambos. El link test ATP→Story es administrativo: une Plan a Story en el grafo sin inflar cobertura.

    • detalles

      El ATS (Acceptance Test Set) es la columna vertebral de cobertura: obligatorio por Story aunque tenga 1 TC. Components heredados de la Story son mandatory (sin ellos los filtros por módulo no lo encuentran). Las listas del ATP y del ATR se derivan de la membresía ATS — nunca se mantienen 3 listas a mano: se desincronizan sin que nadie lo note y la cobertura queda corrupta.

    • detalles

      Se pregunta el formato una vez por batch (no por TC): Gherkin para flujos candidatos a automatización, Manual para exploración con juicio humano — la sugerencia es solo sugerencia, elige el usuario.

      Gotcha de Xray Cloud: descarta silenciosamente los steps pasados inline en test create — por eso los Tests Manual se crean sin steps y cada step se agrega uno por uno (Gherkin no aplica, es un solo campo).

      Parent = épica QA Test Repository (los TCs viven en el repositorio de pruebas, no en artefactos de ejecución). El workflow TC es Draft → In Design → READY: dejar TCs en Draft bloquea Stage 2 (Ejecución).

    • detalles

      El ATR (Test Execution) es el registro de la corrida. Dos reglas:

      • El ambiente es obligatorio (hard gate): crear la Execution sin ambiente significa que Stage 1 (Planificación) no está terminado (DoD = lista de condiciones que deben cumplirse para dar una etapa por hecha). El ambiente se toma de active_env en .agents/project.yaml al momento de crearla.
      • Se crea UN ATR por Story — nombre fijo ATR: {KEY}: Story Testing — y se reutiliza durante todo el sprint: si la misma Story se prueba varias veces (sesiones, retest), se usa el mismo ATR, nunca se crea otro. Un sprint con 5 Stories tendrá 5 ATRs, uno por Story.
    • detalles

      Sin Xray no hay work types Test Plan/Execution/Set: todo vive en campos custom de la Story. El ATR se crea ahora como placeholder ("pending execution") y se llena en Stage 3 (Reporte). Los TCs no se crean como issues en sprint (un Test nativo es documentación, no unidad de ejecución) — se quedan como outlines y Stage 4 (test-documentation) decide cuáles merecen ser ítems de regresión.

  • detalles

    El workflow del ATP es Planning → READY → Completed. Stage 2 (Ejecución) asume que el ATP está en READY: si queda en Planning, la fase de ejecución queda bloqueada (el equipo no sabe si el plan está cerrado o en borrador). El transition slug es Designed.

  • detalles

    Cerrar el ATS requiere campos VCR (VCR Estimation, To Be Automated, In Regression Plan) que solo existen cuando /test-documentation calcula el ROI en Stage 4 (test-documentation). Cerrarla ahora provocaría que Stage 4 (test-documentation) no pueda completar la transición.

  • detalles

    Verificación post-escritura: un link mal creado (dirección invertida, slug equivocado) hace que Xray muestre cobertura 0% o que el grafo Jira tenga huérfanos — y nadie lo nota hasta que fix-traceability (o un manager) lo ve. Se verifica: los 3 links test con dirección correcta + membresía ATS completa + que las listas del Plan/Ejecución = ATS.

Ejecución (Stage 2)

  • detalles

    El smoke valida el ambiente; la trifuerza valida el ticket bajo prueba (la story y sus ACs). Si el ambiente está roto (login caído, 500s), cada intento de probar la story produce falsos positivos que terminan como defectos inventados — el No-Go ahorra ese ruido. Orden fijo: smoke → Go → exploración. Un smoke fallido siempre detiene; un FAIL dentro de la exploración no (va al protocolo graduado).

  • detalles

    Trifuerza = probar las 3 capas: UI (qué ve el usuario), API (qué responde el contrato), DB (qué quedó persistido). "Más allá de los outlines" es el principle AC-floor: ejecutar el plan es el mínimo, explorar el riesgo fuera de él (particiones nuevas, transiciones, anomalías) es donde aparecen los defectos reales. Se elige el subconjunto según lo que cambió en el código, no las 3 siempre.

  • detalles

    Maniobra de 3 pasos: el MCP OpenAPI solo lee esquemas (descubrir endpoints, shapes) pero no ejecuta requests autenticados. El token se acuña con bun run api:login → .auth/tokens.env. La ejecución autenticada es curl — nunca vía el MCP. Es doctrina fija: probar APIs "por el MCP" da 401s fantasma o peor, ejecuciones sin traza.

  • detalles

    Carpeta: .context/PBI/epics/EPIC-…/stories/STORY-…/evidence/. El token step{NN} ata cada archivo al paso de reproducción — el reporte de defecto referencia "step3" y el reviewer abre exacta esa imagen. Curar, no volcar: 1-4 shots con caption de negocio ("descuento ahora es línea propia, total sin cambio"), nunca capturas de navegación intermedia. Verificar en disco cada archivo antes de referenciarlo.

  • detalles

    Stage 3 (Reporte) no puede reportar lo que Stage 2 (Ejecución) no registró. En xray cada TC corre como Test Run dentro del ATR (PASS/FAIL/BLOCKED/ABORTED) con comment opcional (key del defecto si FAIL); en native se actualiza el estado del outline. Este estado es lo que alimenta el TEST CASES del ATR y el pass-rate final.

  • detalles

    Workflow TC: Draft → In Design (Stage 1: Planificación) → READY (Stage 2: Ejecución) → MANUAL/In Review (Stage 4: test-documentation). Stage 2 (Ejecución) ejecuta TCs que están en In Design y los deja en READY. La transición final READY→MANUAL la decide Stage 4 (test-documentation) tras el ROI — sprint-testing no clasifica Candidate vs Manual, para eso está /test-documentation.

  • detalles

    Protocolo graduado que evita dos extremos:

    • Bloqueante (smoke fallido o ambiente caído, corrupción de datos, explotabilidad de seguridad) → pausar el dispatch, presentar el defecto, esperar decisión. Nunca seguir mientras esté sin resolver.
    • No bloqueante (cosmético, validación menor, edge en TC no crítico) → el pass lo registra y continúa; se sube al cierre de Stage 2 (Ejecución). Parar por un padding roto destruye la cadencia.

    Un FAIL no es automáticamente Crítico — triage primero (severidad por matriz de reporting).

  • detalles

    Un FAIL en cookies/CSP/HSTS/SDK-by-design frecuentemente tiene explicación de framework ("Secure/HttpOnly son defaults bajo HSTS preload") — bloquear la Story ahí cuesta un ciclo de fix por un no-defecto.

    El gate exige 3 pasos antes de cualquier transición bloqueante: (1) enunciar la hipótesis de mitigación, (2) citar un dato verificado (header observado, línea de config, doc del framework), (3) exponer al usuario — QA nunca degrada un hallazgo de seguridad en silencio. Si la hipótesis se confirma → PASSED WITH ISSUES (GO-with-debt), no bloquea; el resultado queda registrado en Observations del ATR como audit trail.

Reporte (Stage 3)

  • detalles

    Un ATR con NOT RUN es un reporte que miente sobre el estado real — si hay TCs sin correr, se vuelve a Stage 2 (Ejecución), no se reporta. Los defectos deben estar confirmados y reportados porque el ATR los referencia por key.

  • detalles

    El ATR (Acceptance Test Results) es el registro de auditoría de la corrida — el comentario QA es el resumen, el ATR es la prueba. Mismo cuerpo en ambas modalidades, solo cambia el contenedor (campo vs Test Execution). Formato plain-text plano para que sobreviva la conversión a Jira renderer.

    • detalles

      Los 3 valores de Result: PASSED (todo verde), FAILED (al menos uno rojo), PASSED WITH ISSUES (todo verde pero con observaciones relevantes o resultado del gate de recalibración). El ratio (ej. 11/12) da el pass-rate de un vistazo.

    • detalles

      2-4 líneas para quien no va a leer los TCs uno por uno: alcance probado + veredicto. Es lo primero que lee PM en el reporte.

    • detalles

      Lista plana {US_ID}: TC#: should {outcome} [when/if {condition}] ... {status} (solo modalidad Xray — en jira-native los TCs viven como outlines en Stage 2). Los statuses vienen del campo de Execution Status (Run), no del workflow del Test — en native, de la actualización de Stage 2 (Ejecución).

    • detalles

      Qué datos concretos se usaron (pedido #12345, usuario juan.test\@…). Permite reproducir la corrida y depurar falsos positivos ("¿falló o el dato ya estaba corrupto?").

    • detalles

      Keys clicables de los defectos reportados + su severidad. Si no hay defectos: "None" explícito — sección vacía genera duda, no alivio.

    • detalles

      El "no bloqueó pero vale anotar": feedback UX, edge cases observados, deuda detectada. Aquí también queda el audit trail del gate de recalibración (hipótesis + dato + decisión) — explica por qué un P1 no bloqueó la Story.

    • detalles

      Insumo directo para Stage 4 (test-documentation): candidatos informales a automatizar (juicio de QA, sin fórmula ROI — eso lo hace Stage 4), testing futuro, mejoras de proceso. Es el puente QA → /test-documentation.

  • detalles

    El contenedor lo decide la modalidad resuelta en Session Start (quedó persistida en test-session-memory.md). No se mezclan ramas: subir al contenedor equivocado = ATR invisible para fix-traceability.

    • detalles

      El ATR es el ítem Test Execution (ya creado en Stage 1 (Planificación) con ambiente). Stage 3 (Reporte) lo llena: descripción = cuerpo ATR, Begin Date = fecha de test, End Date = ahora, un Update Run por TC con su resultado (comment opcional con la key del defecto si FAIL). Cierre: transición Complete → Close. Señal de completitud: todos los Runs en estado terminal (no TODO/EXECUTING).

    • detalles

      Sin ítem Test Execution, el ATR va al campo custom de la Story (o al comentario fallback si el campo no existe). Los estados por TC viven en el cuerpo del ATR (sección TEST CASES): Stage 2 (Ejecución) marca los outlines PASSED/FAILED en test-session-memory.md — no son issues Jira — y Stage 3 (Reporte) los vuelca al ATR. El loop de Test Status por issue solo corre si hay Test issues linkados al ATR; en el flujo normal no los hay (se crean y linkean en Stage 4, después) → no-op. Señal de completitud: campo poblado con cuerpo completo (sin placeholder).

  • detalles

    Al cerrar Stage 3 (Reporte) el plan también cierra: Planning → READY → Completed. Dejar el ATP en READY tras reportar deja el artefacto "a medio cerrar" — el próximo lector no sabe si la ejecución se completó.

  • detalles

    Cada FAIL se convierte en ticket solo tras confirmación humana de que es defecto real (jamás reportar automáticamente) + retest de reproducibilidad + búsqueda de duplicados con el patrón de título. El template de reporte comparte estructura para Bug/Defect/Improvement — lo que cambia es la clasificación y los campos.

    • detalles

      La clasificación responde a si lo roto ya está en producción — no al lugar donde lo encontraste (puedes reproducir en localhost pero si aún es pre-release = Defect):

      • Bug — ya live sobre Staging (producción), visible para usuario final: escapó de la puerta del sprint.
      • Defect — aún pre-release: salida normal del testing del sprint (contenido, no escapado).
      • Improvement — nada roto: es una mejora o un AC sub-especificado que QA surfació yendo más allá del criterio.

      Usar "Bug" para todo distorsiona las métricas de calidad (escape rate vs defect rate).

    • detalles

      Título — <EPIC>: <COMPONENT>: <summary>: tres segmentos separados por :. En cualquier lista de defectos, el primer segmento agrupa por épica y el segundo por módulo — se sabe de qué zona es el defecto sin abrir el ticket. Ejemplo real: CheckoutFlow: Payment: Error message not shown for incorrect password.

      Descripción — 5 secciones, en este orden:

      • SUMMARY — un párrafo: qué falla y qué impacto tiene.
      • STEPS TO REPRODUCE — pasos numerados; el paso 1 es siempre la precondición (usuario, login, estado de datos), luego navegación → acción que dispara → observación. "Le falló una vez" sin pasos reproducibles no es un defecto.
      • TECHNICAL ANALYSIS — archivo, función, llamada de red, errores de consola (lo que se sepa al reportar).
      • IMPACT — usuarios afectados, funcionalidad bloqueada, impacto de negocio.
      • RELATED STORIES — stories relacionadas / issues que bloquea.

      Campos del reporte — junto a la descripción: Actual Result y Expected Result (qué pasó vs qué debía pasar). Son custom fields (actual_result / expected_result); si la instancia no los tiene, se agregan al cuerpo como ## Actual Result / ## Expected Result.

      Cada paso puede referenciar su evidencia con {KEY}-step{NN} (p. ej. UPEX-512-step03).

    • detalles

      El campo nativo components es mandatory: identifica el módulo de producto afectado y alimenta los filtros/dashboards por área. Debe pre-existir en el módulo Components de Jira — si el módulo no existe, se pide al admin, no se crea una component ad-hoc desde QA.

    • detalles

      Modelo de 3 ejes — separarlos evita que el board de desarrollo se contamine con artefactos QA:

      • Parent = épica de proceso QA (bucket de defects). El campo Parent nunca apunta a una épica de producto ni a la Story — la Story sí se vincula, pero por el eje Link.
      • Link = la Story fuente (trazabilidad del requisito que falló).
      • Components = el módulo de producto.

      La épica QA Defect Management se busca y si no existe se crea — es el contenedor de todos los bugs/defects del proyecto.

    • detalles

      La línea "Related Stories" en texto plano es solo documentación humana; el borde operativo es el issuelink real (Story es outward party = causes, Defect es inward = is caused by). Se resuelve el tipo por slug y se verifica la dirección tras crear — dirección invertida rompe los reportes de trazabilidad que caminan el grafo.

    • detalles

      qa_assignee: dueño QA del reporte (quien lo fileó) — distinto del assignee nativo que queda libre para el triage de dev. Solo se escribe si está vacío.

      Priority se deriva de Severity para que la cola sea consistente: Critical→Highest, Major→High, Moderate→Medium, Minor→Low, Trivial→Lowest. Es la regla por defecto, no la verdad: un defecto puede ser Trivial en severidad pero prioritario para el negocio (campaña lanzando hoy, cliente clave) — en ese caso se hace override de Priority con justificación de 1 línea (urgencia de negocio ≠ severidad técnica).

      La matriz de campos obligatorios va a custom fields si los slugs existen en jira-fields.json; si un slug no existe, el valor cae a una sección de la Description con heading estandarizado (degradación documentada, no error). Los labels bug + exploratory-testing alimentan los filtros de QA.

      ![](ruta) en Jira no incrusta la imagen — queda como link muerto. El helper sube el archivo y la postea inline en un comment como imagen real: el reviewer ve la pantalla rota de un vistazo sin abrir el panel de adjuntos.

      • Una llamada por archivo — el helper adjunta un solo archivo por ejecución; 3 screenshots = 3 llamadas al script.
      • --caption = business outcome — el caption dice qué falló para el usuario, no el nombre del archivo. El reviewer lee el caption antes que la imagen: es el título del hallazgo. ✗ screenshot3.png · ✗ defecto evidencia → ✓ Paso 3 — no se muestra el mensaje de validación
    • detalles

      Los defectos son "coverable": en Xray el fix se verifica con un Test de reproducción. Flujo en 4 pasos:

      1. Cuándo se crea — en fix-verification (al verificar el fix), no antes. Antes de esa fase, las trazas de "TC faltante" en el defecto son esperadas — no se corrigen.
      2. Cuántos Tests — 1 por defecto. Solo se planean más (1:N) si el alcance cubre condiciones genuinamente distintas, con justificación escrita de test-design.
      3. Vínculo — Defect↔Test con link type test.
      4. Ejecución — correr en la Execution ReTest: {BUG_KEY}: {summary}, siempre con ambiente (Test Environment), y registrar PASSED/FAILED.

      jira-native: no hay TCs en sprint — el ticket del defecto (con sus pasos de repro) es el caso de retest; no se crea un Test aparte.

  • detalles

    4 templates cubren los caminos (Story/defecto × pass/fail) — estandarizan lo que PM/Dev leen al llegar al ticket. Estructura común: Environment + Result + test data + behaviours verificados/fracasados + artefactos (ATP/ATR/TC keys).

    Regla de link real (binding): cualquier key que el comentario nombre como blocker o defecto reportado (DEFECT: KEY, back-references) debe ser un link clickeable — las keys en texto plano no se auto-linkean en ADF y un blocker no clicable derrota el propósito de nombrarlo. La traza en el grafo (issuelink) es aparte y también obligatoria: el link sirve al lector, el issuelink sirve al grafo.

  • detalles

    Evidence Handoff: lista corta y rankeada de qué archivos del evidence/ van al ticket. La lista cumple 4 reglas:

    • La "money shot" va primero — si hubo anotación del defecto con bug-screenshot-annotation, esa PNG se pone al inicio de la lista.
    • Cada imagen lleva caption de negocio — qué falló para el usuario (no el nombre del archivo).
    • Skip list incluida — se lista qué archivos se capturaron pero no se mandan al ticket, con el motivo de descarte.
    • Bloques API redactados — credenciales y tokens se sustituyen por <redacted> antes de incluirlos.

    La lista rankeada y la oferta van en chat — no en el cuerpo del comentario Jira. Se ofrece publicar las imágenes con el helper y el humano confirma antes de ejecutar.

  • detalles

    La transición codifica el veredicto de QA en el workflow — sin ella el ticket queda mintiendo en el tablero (una Story FAIL en "In Test" para siempre). La tabla aplica el flujo de decisión: PASSED → sign-off; FAILED con defecto confirmado → bloqueado (+ link de dependencia); no bloqueante → queda en In Test con el defecto; recalibrada → sign-off con deuda.

    ⚠ Nunca marcar QA Approved sin sign-off + ATR completo (anti-patrón S1/S3). Si la transición defect_reported → BLOCKED se dispara, el link blocks (Defect → Story) es obligatorio: el cambio de estado solo no crea la arista de dependencia.
  • detalles

    Cuando hay verdes y rojos (resultados mixtos): el ATR queda en PASSED WITH ISSUES. Se reporta un defecto por cada causa raíz distinta, no uno por cada TC rojo — si 3 TCs rojos comparten la misma causa raíz, va 1 solo defecto (y antes se busca si ya existe un ticket con el mismo título). No se bloquea el handoff a Stage 4 (test-documentation): los TCs que pasaron siguen siendo elegibles para evaluación de ROI — un fallo no anula el valor de lo que sí funcionó.

  • detalles

    Stage 4 (test-documentation) consume lo que Stages 1-3 (Planificación → Reporte) produjeron (outlines + evidencia de ejecución) para calcular ROI y decidir qué TCs persisten como regresión (Candidate/Manual/Deferred). Si todo es Manual-only y nada vale automatizar → cerrar sin handoff. Bucle: Story FAILED → esperar fix → re-ejecutar Stage 2 (Ejecución) en los TCs fallidos → Stage 3 (Reporte) otra vez.

Modo bug/defect (retest de fix)

Notación: ticket = contenedor en Jira (issue). defecto = el problema encontrado (pre-release); bug = el problema encontrado (post-release). reportar = el verbo.

  • detalles

    El mismo flujo que en las Stories pero aplicado al ticket del bug/defect. Veto SKIP (solo CSS, docs, copy estático, infra o refactor sin cambio funcional → solo verificar el fix en código + comentario en el ticket, sin ATP/ATR) gana sobre el score. Veto REQUIRE (money/billing, integridad de datos en entidades core, auth, integraciones externas, fix en módulo crítico, cálculos) fuerza ATP + ATR completos aunque el score sea bajo. Si ningún veto aplica → risk score (0-3 LOW, 4-7 MEDIUM, 8+ HIGH). Reducir un typo a un ATP completo es el desperdicio que el veto evita; dar por bueno un fix de billing sin ATP es el riesgo que REQUIRE evita.

  • detalles

    El ATP del ticket del bug/defect reemplaza las fases de análisis de Story (el defecto reportado es la especificación): pasos exactos del ticket original (esperado vs actual), hipótesis de causa desde lectura de código, los pasos que ahora deben pasar en staging, qué áreas adyacentes podría haber roto el fix, y queries DB si tocó estado persistido (¿huérfanos, registros a medias?).

  • detalles

    La ejecución de retest es un Test Execution propio del ticket del bug/defect (nombre ReTest: …), no el ATR de la Story. Mismo hard gate: sin ambiente no se crea — el ambiente resuelve de active_env al momento de creación.

  • detalles

    El orden importa: (1) reproducir el bug/defect original — si ya no reproduce, el fix funciona; (2) verificar el comportamiento esperado correcto, no solo "ya no truena"; (3) regresión ligera en áreas vecinas que el fix pudo tocar; (4) si el bug/defect corrompía datos, validar en DB que no quedaron registros huérfanos.

  • detalles

    Template C = fix confirmado → bug/defect pasa a Closed; Template D = sigue reproduciéndose → vuelve a dev en Ready For QA.

    Si el bug/defect es regression-worthy (área crítica, ya escapó una vez), Stage 4 (test-documentation) debe garantizar un Test persistente que lo cubra — regla golden: reusar el Test fallido existente (o el repro de esta pasada) o crear uno. Nunca duplicar. No todo bug/defect califica: un typo one-time en área estable se trata como un test fallido, no como candidato de regresión.
