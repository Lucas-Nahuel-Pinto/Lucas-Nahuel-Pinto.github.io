Plan (Phase 1)

  • detalles

    Es el gate entre Phase 1 y Phase 2 — no existe "codear primero, planear después" (anti-pattern T2: incluso un regression test simple requiere su plan antes del código).

Code (Phase 2)

  • detalles

    El verify es en este orden exacto y no se salta: bun run test <path> → bun run types:check → bun run lint:check. Si alguno falla, se arregla ANTES de avanzar a Review — no se llega a Phase 3 con el local roto.

    Steps classes (tests/components/steps/*Steps.ts) no se registran en ningún fixture: los tests y setup los instancian directamente.

  • detalles

    Solo existen esos 3 fixtures (tests/components/TestFixture.ts). Reglas: tests/integration/** casi siempre { api }; tests/e2e/** con { ui } si no hay setup vía API, si no { test }.

    Nunca { ui } en un test que no toca la UI — abre un browser para nada. Fixture equivocado = tests API lentos o contexto UI faltante.

  • detalles

    clickLoginButton() no es un ATC; loginWithValidCredentials(credentials) sí. Si el método es un one-line wrapper de page.click(), borrarlo.

    Helpers vs ATCs: un GET read-only es helper (sin @atc, opcional @step); una acción que cambia estado es ATC. Un GET dentro de un ATC para verificar que la acción funcionó está bien — el GET solo no es ATC.

  • detalles

    La regla anti-extracción prematura es deliberada: el selector vive junto al comportamiento que lo usa. Cuando el mismo locator aparece en 2+ ATCs del componente, se promueve a función privada dentro de la clase — jamás a un módulo de locators.

  • detalles

    Named object parameters superan a las listas posicionales en mantenibilidad y autocomplete: firmas como createUser({ email, role, plan }) sobreviven a agregar un cuarto dato; createUser(a, b, c) no.

  • detalles

    ../../../ rompe al mover archivos y lo rechaza el lint (anti-pattern T5). Los aliases viven en la config de path mapping de TypeScript/Playwright.

  • detalles

    LOCAL_USER_* / STAGING_USER_* y sus passwords viven en .env; nunca inline en spec, fixture ni archivo de datos (anti-pattern T6).

    Datos únicos por test vía TestContext.generateUserData() o helpers de faker — el estado compartido entre tests es la receta para ejecuciones en orden aleatorio rotas.

  • detalles

    Las mismas esperas de un mismo par (precondition, action) son aserciones del MISMO TC — no se parte un TC en "panel A / panel B / panel C" (gotcha 2, el anti-patrón más diagnosticado en reviews).

    EP: mismo output esperado = un ATC parametrizado — tres ATCs que todos devuelven 401 para login inválido se fusionan en loginWithInvalidCredentials(payload).

  • detalles

    Componentes: {Resource}Api.ts / {Page}Page.ts — un componente por archivo, un archivo por feature. Tests: applyDiscount.test.ts, nunca discount.test.ts.

    El describe puede llevar el ticket ID cuando el archivo pertenece a un solo ticket. El ticket ID en cada test() es lo que permite el trace Vía @atc('TICKET-ID') de vuelta al TMS.

  • detalles

    El link resuelve el slug {{jira.link_types.test_automation}} — nunca un literal. Labels son mutuamente excluyentes: automation-candidate se quita al poner automated.

    Timing: los labels cambian cuando el TC alcanza AUTOMATED — que ocurre tras el PR final de la suite en main con CI green, no al mergear en el integration trunk.

Review (Phase 3)

  • detalles

    Pueden correr en paralelo como sub-verificaciones independientes, pero el ACCEPT requiere los 3 exit 0. Un solo rojo = REJECT.

    La suite local pasa sin retries: si un test solo pasa al retry, es flaky, no passing (gotcha 11).

  • detalles

    Error protocol del orchestration: el fallo se reporta con su contexto completo y las opciones (retry / skip / abort) las decide el usuario. Auto-fixear en silencio oculta la causa raíz y ensucia el diff sin diagnóstico.

  • detalles

    El checklist se corre sobre los archivos nuevos/modificados. No es "casi verde": cualquier ítem rojo bloquea el merge hasta arreglarse.

  • detalles

    Gate adversarial opcional: dos judges ciegos en paralelo contra el diff, aprueba solo si ambos coinciden. Se invoca por decisión del usuario por ticket — nunca automático.

  • detalles

    Los quality gates no cubiertos por los 3 comandos: registro en fixture (Steps jamás), IDs de ATC ligados a un test case real del TMS, y el naming (PascalCase componentes / camelCase con verbo para tests).

No hacer

  • detalles

    Saltarse el ROI verdict de Stage 4 produce suites flaky y de bajo valor: se automatiza esfuerzo donde no va a re-ejecutarse. (Anti-pattern T1.)

  • detalles

    Plan → Code → Review es non-negotiable. El atajo directo a código es la vía rápida a un test que no cubre lo que creías. (Anti-pattern T2.)

  • detalles

    Tests que aplanan las capas se rechazan en Review. La doctrina completa está en references/kata-architecture.md. (Anti-pattern T3.)

  • detalles

    ATCs son mini-flows atómicos; un ATC que invoca a otro acopla sus fallos y hace imposible reusar la cadena por separado. (Anti-pattern T4.)

  • detalles

    Los aliases del repo: @api/, @ui/, @schemas/, @utils/, @TestContext, @variables, @TestFixture. (Anti-pattern T5.)

  • detalles

    Todo desde .env vía config.testUser de @variables. Un password en el repo es una fuga permanente, aunque sea "de tests". (Anti-pattern T6.)

  • detalles

    Los IDs numéricos de campos rotan con cada workspace; resolverlos contra .agents/jira-fields.json + jira-required.yaml hace que el test code sobreviva. (Anti-pattern T7.)

  • detalles

    Bajo estrategia sdet, el trabajo no-test adyacente tampoco viaja en un ticket branch test/* — va por una Plus Branch (docs/*/chore/*/fix/* → integration trunk). (Anti-pattern T8.)

  • detalles

    Esperas correctas: waitForSelector, waitForResponse, waitForLoadState('networkidle') o atributos como data-loaded="true". El sleep fijo es la causa número uno de tests lentos y flaky a la vez.

  • detalles

    Un retry enmascara el problema en vez de diagnosticarlo: si un test solo es verde al segundo intento, hay una race o un wait mal puesto — investigar, no reintentar. (Gotcha 11.)
